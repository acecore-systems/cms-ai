# 2026年10月の承認済み月額上限12.10 USD

利用者の2026-10-24の明示承認により、JSTの2026年10月だけ月額上限を11.89から12.10 USDへ変更する。承認された追加実確認は未使用の1回で、親担当が実行する。通常月7 USD、1回1.25 USD、10月26日分1.25 USDの留保、全工程30分、既存の生成・校閲・Draft契約は変更しない。

`monthBudgetMicros("2026-10")` は12,100,000 microUSD。新モデルjobの `newJobMonthLimit` は10月26日00:00 UTCより前に1,250,000を引いて10,850,000とし、同時刻以後は12,100,000になる。JSTの11月以降および他年10月は7,000,000。

親が取得した現在の予約累計9,707,766に対し、留保後の残額は1,142,234。直近9言語の全工程最大1,138,828との差は3,406 microUSDである。これは現時点の見積もりであり、候補・予約額が変わった場合には再度無料preflightとSQLの原子的予約判定を行う。生成成功の保証や、上限を超える実行の承認ではない。

## migrationと旧状態

追加 `0035_seo_october_budget_1210.sql` だけを適用する。既存migrationを編集せず、変更する既存schemaは次の3triggerの金額定数のみ。

- `seo_budget_cap`：10月の月累計上限12,100,000。
- `seo_fallback_first_call_fit`：初回呼出し前の全工程最大費用と月累計の上限12,100,000。
- `seo_model_reservation`：10月26日00:00 UTC前の全phase予約上限10,850,000。

生台帳、失敗・不明な予約、旧run/job、モデルpin、記事lock、receipt、監査、期限は更新・削除しない。旧jobの契約やrun上限は保持する。旧jobを再送する実装も追加しない。

## 本番反映順序

CMSはmainへのpushで本番buildが自動起動するため、**PR mergeより先に0035を適用する**。

1. 親担当がfreshな全旧行/schemaと対象migration hashを取得し、上記3trigger以外の差分がないことを確認する。
2. 本番0035を適用し、全旧行不変・3triggerの金額値を再照合する。旧コードはより小さい額でpreflightするため、この段階では保守側になる。
3. PRのCI成功・レビュー後にmergeし、Git push build成功と正確なmerge SHAの本番versionを確認する。
4. 新しいrunとして承認済み1回を親が実行する。直前の残額・留保・全工程最大を再確認し、AI前skipや生成・校閲・Draft結果を区別して記録する。

コード担当はmigration本番適用・merge・deploy・AI呼出しを行わない。金額境界、月/留保時刻境界、run上限、fallback全工程fit、実D1の監査先行batchと競合予約、旧行と他schema保持をローカルで検証する。
